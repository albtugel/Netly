## Текст доклада

**Слайд 1.** Здравствуйте. Меня зовут Алибек Тугельбаев, группа 4ТМ. Тема — Netly, серверная часть сервиса планирования личного бюджета. Покажу, как результаты практических работ 1–4 складываются в один проект: от бизнес-задачи до защиты API.

**Слайд 2.** Пользователи — студенты и начинающие специалисты, у которых доход из нескольких источников и несколько подписок. Банковское приложение показывает, что уже потрачено, но не отвечает, сколько можно тратить и откладывать в этом месяце. Netly приводит все суммы к месячному эквиваленту и считает свободный остаток. Измеримая польза: остаток и взнос по каждой цели получаются одним запросом, вместо ручной таблицы раз в месяц.

**Слайд 3.** Требования записаны шестью пользовательскими историями, они покрывают путь от входа до сводки. На сервере уже реализованы три: подписки и долги, накопительные цели и вход по паролю. Ввод доходов, расходов и сводка — в плане на ПР 5–7, потому что им нужны доходы в Profile Service.

**Слайд 4.** Для двух историй критерии приёмки записаны в формате Given–When–Then, и каждый критерий — автотест. Подписка Netflix за 119.88 в год даёт monthlyCost 9.99. Неверный пароль и несуществующий email дают одинаковый ответ 401, чтобы по ответу нельзя было узнать, зарегистрирован ли адрес.

**Слайд 5.** Сравнивал Swift, Node.js с Express и Python с FastAPI. Решающие критерии — один язык с iOS-клиентом, это общие Codable-модели, и строгая типизация при компиляции. Внутри Swift два фреймворка: Vapor для Profile Service, где связанные данные и аутентификация, и минималистичный Hummingbird для Budget Service, где плоская модель и расчёты. Это тот же выбор, что Django против Flask в Python.

**Слайд 6.** Система из двух сервисов, у каждого своя база. Клиент получает JWT в Profile Service и с ним идёт в Budget Service. Проследим POST /goals. Первый слой, middleware, проверяет подпись токена и достаёт user_id, иначе 401. Контроллер декодирует JSON и валидирует поля, иначе 422. Бизнес-логика считает ежемесячный взнос. Репозиторий выполняет параметризованный INSERT с user_id. Строка из базы возвращается как 201 с заголовком Location. Ошибку на любом слое ловит внешний ProblemErrorMiddleware и отдаёт в едином формате.

**Слайд 7.** Репозиторий — монорепозиторий: документация и контракты в docs, сервисы в services, у каждого свои Sources и Tests. Всё, что меняется между средами — адрес базы, пароль, секрет JWT, порт, — вынесено в переменные окружения. Файл .env в .gitignore, в репозитории только .env.example. Если переменной нет или секрет короче 32 байт, сервис не стартует, а не падает на первом запросе.

**Слайд 8.** ER-диаграмма. В базе бюджета четыре таблицы: подписки, долги, цели и пополнения целей. Пополнения связаны с целью внешним ключом один-ко-многим с каскадным удалением. Таблица users живёт в другой базе, у Profile Service. Внешний ключ между базами невозможен, поэтому user_id — логическая ссылка: значение берётся из подписанного токена, а не из тела запроса.

**Слайд 9.** Схема создаётся только миграциями, их три, и каждая откатывается. Вторая миграция показывает эволюцию схемы: индекс под фильтр целей по статусу добавлен отдельно, после первой версии. Каждый индекс отвечает на конкретный запрос. Составной индекс по user_id, status и created_at отдаёт страницу активных целей прямо из индекса, без сортировки. Уникальный индекс по email ускоряет вход.

**Слайд 10.** Пример транзакции — пополнение цели. В одной транзакции вставляется пополнение и увеличивается накопленная сумма цели. Если сумма превысит целевую, срабатывает CHECK в базе, транзакция откатывается целиком, и клиент получает 422. Проверка именно в базе, а не чтением перед записью, поэтому два параллельных пополнения не обойдут ограничение. Справа — остальные ограничения: NOT NULL, CHECK, NUMERIC для денег, внешний ключ и уникальность.

**Слайд 11.** Контракт REST. Ресурсы — существительные во множественном числе под /api/v1, действие задаётся методом. Пополнения вложены в цель, потому что без цели не существуют. Подписки и долги повторяют ту же пятёрку операций. Всего 18 операций в Budget Service и 5 в Profile Service.

**Слайд 12.** Контракт описан формально в OpenAPI 3.1, для каждого сервиса свой файл. У каждой операции перечислены все коды ответа, примеры взяты из реальных ответов. Файлы проверяются линтером Redocly без ошибок. На слайде операция пополнения цели: 201, 404 для чужой или несуществующей цели и 422.

**Слайд 13.** Валидация идёт в два этапа: сначала декодирование JSON, затем бизнес-правила, причём ошибки всех полей возвращаются разом. Формат ошибок единый для обоих сервисов — RFC 9457 problem+json: машинный code, понятный человеку detail и массив errors по полям. 400 — тело не JSON, 422 — JSON корректный, но нарушены правила, 409 — дубликат.

**Слайд 14.** Списки отдаются страницами. limit от 1 до 100, по умолчанию 50; offset от нуля. Для целей есть фильтр status. Порядок стабильный, по created_at и id, поэтому страницы не перекрываются. total позволяет клиенту построить навигацию. Значение вне диапазона — 422.

**Слайд 15.** Регистрация: email и пароль проверяются, пароль хешируется bcrypt с cost 12 в пуле потоков, чтобы не блокировать event loop. В базе хранится только хеш с солью. Вход: хеш сверяется, Profile Service подписывает JWT алгоритмом HS256. В токене sub — id пользователя, role, время выдачи и срок действия — 15 минут. Budget Service проверяет подпись тем же секретом, не обращаясь к Profile Service.

**Слайд 16.** Матрица доступа. Гость может только зарегистрироваться и войти. user и admin работают только со своими записями бюджета; чужая запись отвечает 404, чтобы не раскрывать само её существование. Список пользователей — только admin, user получает 403. Проверка на двух уровнях: middleware на группе маршрутов, до контроллера, поэтому новый эндпоинт нельзя забыть защитить; и условие user_id в каждом SQL-запросе.

**Слайд 17.** Пять угроз из OWASP API Security Top 10 2023. BOLA — доступ к чужому объекту по id: закрыт фильтром user_id. Слабая аутентификация: bcrypt, короткий срок токена, длинный секрет. Mass assignment: роль и user_id из тела игнорируются. Неограниченное потребление ресурсов: limit не больше 100. BFLA — вызов чужой функции: RoleGuard. Для каждой меры есть автотест, его имя в правой колонке.

**Слайд 18.** Это реальные ответы сервисов, снятые скриптом scripts/demo-auth.sh. Цель создана с токеном из Profile Service — 201. Некорректное тело — 422 со списком всех ошибок. Обычный пользователь на /admin/users — 403. Чужая цель — 404. Могу показать то же вживую.

**Слайд 19.** ПР 1–4 выполнены: 23 операций API, 73 автотестов, 3 миграции. До СРС 2 — доходы и расходы в Profile Service, расчёт свободного остатка с распределением по целям и Spending Service. Риски: Budget будет синхронно зависеть от Profile при расчёте остатка; нет ограничения частоты попыток входа и отзыва токена до истечения срока — это в плане.

**Слайд 20.** Итог: проект — одно целое, каждая история доведена до кода и теста. Спасибо, готов ответить на вопросы.

## Ответы на контрольные вопросы

**1. Почему эта предметная область и этот стек? Какие альтернативы отклонены?**
Личный бюджет — задача с расчётной частью: доходы и платежи в разных периодах нужно привести к месяцу и распределить остаток по целям, это больше, чем CRUD. Стек — Swift, потому что клиент на SwiftUI: общие `Codable`-модели и один язык. Node.js + Express и Python + FastAPI отклонены: другой язык, а строгие типы там только опционально. Внутри Swift: Vapor для Profile (связанные данные, аутентификация, Fluent и JWT готовы), Hummingbird для Budget (плоская модель, расчёты, меньше зависимостей).

**2. Путь одного HTTP-запроса.**
`POST /api/v1/goals` → Hummingbird router → `ProblemErrorMiddleware` (обёртка для ошибок) → `JWTAuthenticator` (подпись, срок, `sub` → `user_id`; иначе 401) → `ResourceController.create` (декодирование JSON и `Validator`; иначе 422) → `GoalFields` и `MonthlyEquivalent` (расчёт `requiredMonthlyContribution`) → `PostgresRecordRepository.create` (`INSERT … RETURNING` с параметрами `$1…`, `user_id` из токена) → PostgreSQL `netly_budget` → строка возвращается в контроллер → `201 Created`, заголовок `Location`, JSON цели.

**3. Чем отличаются 400, 401, 403, 404 и 422? Примеры.**
- 400 — тело не разбирается как JSON: `POST /api/v1/auth/login` с телом `{` → `malformed_json`.
- 401 — нет токена, он подделан или истёк: `GET /api/v1/goals` без заголовка → `Missing bearer token`.
- 403 — токен верный, но роли не хватает: пользователь с ролью `user` на `GET /api/v1/admin/users` → `Requires the admin role`.
- 404 — нет такой записи у этого пользователя: чужая цель по её id → `Goal … was not found`.
- 422 — JSON корректный, но нарушает правила: `priority: 11` → `out_of_range`; пропущенное поле → `required`.

**4. Какие операции идемпотентны?**
`GET` (ничего не меняет), `DELETE` (после первого вызова записи нет; повтор вернёт 404, но состояние то же), `PATCH` в нашем API (поля задаются абсолютными значениями, повтор даёт тот же результат). `POST` не идемпотентен: два `POST /goals` создадут две цели, два пополнения увеличат сумму дважды. Повторная регистрация вернёт 409.

**5. Почему такая структура URI?**
Ресурсы — существительные во множественном числе, действие задаёт метод. Версия `/api/v1` в пути позволит выпустить v2, не ломая клиента. Пополнения вложены в цель (`/goals/{id}/contributions`), потому что без цели не существуют. Владельца нет в URI (`/users/{id}/goals`): он берётся из токена, поэтому подставить чужой id невозможно.

**6. Что будет без обязательного поля?**
`422`, `code: validation_failed`, в `errors` — `{"field": "password", "code": "required", "message": "Field is required"}`. Формат — RFC 9457 `application/problem+json`, общий для обоих сервисов.

**7. Какие индексы и какой запрос ускоряет каждый?**
- `goals_user_status_idx (user_id, status, created_at, id)` — `GET /goals?status=active`, фильтр и сортировка из индекса.
- `subscriptions_user_created_idx`, `debts_user_created_idx`, `goals_user_created_idx (user_id, created_at, id)` — списки с пагинацией.
- `subscriptions_user_name_key (user_id, lower(name))` — уникальность имени подписки, дубль → 409.
- `goal_contributions_goal_created_idx (goal_id, created_at, id)` — история пополнений и каскадное удаление (под FK PostgreSQL индекс сам не создаёт).
- `users_email_key (email)` — поиск при входе и уникальность email.

**8. Какие ограничения целостности?**
NOT NULL на всех полях, кроме `note`; CHECK: суммы > 0, `saved_amount` ≤ `target_amount`, `priority` 1–10, допустимые значения `status`, `billing_cycle`, `role`, длина строк, email в нижнем регистре; `NUMERIC(12,2)` для денег; FK `goal_contributions.goal_id → goals.id ON DELETE CASCADE`; UNIQUE на имя подписки у пользователя и на email.

**9. Какая операция в транзакции и что при сбое?**
`POST /goals/{id}/contributions`: `INSERT` в `goal_contributions` и `UPDATE goals SET saved_amount = saved_amount + amount`. Если сумма превысит цель, CHECK `goals_saved_within_target` отклоняет UPDATE, PostgreSQL откатывает всю транзакцию — записи о пополнении тоже нет, клиент получает 422 `exceeds_target`. При обрыве соединения посреди транзакции PostgreSQL тоже откатывает её. Откат виден в логе PostgreSQL: `docs/verification.md`.

**10. Как хранится пароль?**
Только bcrypt-хеш с солью и cost 12 (`$2b$12$…`). bcrypt медленный намеренно: перебор утёкшей базы становится дорогим, а соль не даёт использовать готовые таблицы. SHA-256 не подходит — он быстрый. Пароль ограничен 72 байтами, потому что bcrypt игнорирует остальное. Хеширование выполняется в пуле потоков, чтобы не блокировать event loop.

**11. Что в токене и каков срок?**
JWT HS256: `sub` — id пользователя, `role` — `user` или `admin`, `iat` — время выдачи, `exp` — `iat` + 15 минут. Подписан общим `JWT_SECRET` (не короче 32 байт). Пароля и личных данных в токене нет: payload читается без ключа.

**12. Где проверяются права и почему там?**
В middleware на группах маршрутов: `AccessTokenAuthenticator`/`JWTAuthenticator` на всей группе `/api/v1` (кроме регистрации и входа), `RoleGuard(.admin)` на группе `/admin`. Проверка до контроллера, поэтому новый маршрут в группе защищён автоматически. Владение записью проверяется в SQL (`WHERE id = $1 AND user_id = $2`), поэтому даже ошибка в контроллере не отдаст чужую запись.

**13. Четыре главные угрозы и как проверяется защита.**
- API1 BOLA — фильтр `user_id` во всех запросах, чужая запись → 404; тесты `showHidesOtherUsersRecords`, `anotherUsersGoalIsNotFound`.
- API2 Broken Authentication — bcrypt, токен на 15 минут, секрет ≥ 32 байт, одинаковый ответ на неверный пароль и неизвестный email; тесты `expiredTokenIsUnauthorized`, `tokenSignedWithAnotherSecretIsUnauthorized`, `wrongPasswordAndUnknownEmailFailTheSameWay`.
- API3 Broken Object Property Level Authorization (mass assignment) — `role` и `user_id` из тела не читаются; тест `roleInRegistrationBodyIsIgnored`.
- API5 BFLA — `RoleGuard(.admin)`; тест `userRoleIsForbiddenFromAdminRoutes`.
- API4 Unrestricted Resource Consumption — `limit` ≤ 100, лимит размера тела; тест `listValidatesPaging`. Rate limit на вход — в плане.

**14. Что не реализовано и почему?**
Доходы и обязательные расходы в Profile Service, внутренний эндпоинт `/internal/users/{id}/baseline`, расчёт свободного остатка с распределением по целям, Spending Service. Это темы ПР № 5–7, сначала нужен был фундамент: данные, контракт, безопасность. Из безопасности — ограничение частоты попыток входа и refresh-токены с отзывом.

## Возможные дополнительные вопросы

- **Почему 404, а не 403 для чужой записи?** 403 подтвердил бы, что запись с таким id существует. 404 не раскрывает ничего.
- **Почему нет внешнего ключа на users?** Таблица в другой базе другого сервиса, PostgreSQL не ссылается между базами. Целостность обеспечивает подпись токена.
- **Почему UUID, а не SERIAL?** id нельзя перебрать по порядку, и сервис генерирует его сам до вставки.
- **Почему HS256, а не RS256?** Два своих сервиса, общий секрет проще. Если токен начнут проверять сторонние сервисы, нужен RS256: им достаточно публичного ключа.
- **Что если украдут токен?** Он действует не дольше 15 минут. Отзыв до истечения срока — в плане (refresh-токены).
- **Почему деньги в NUMERIC?** float не представляет точно 0.10, ошибки округления накапливаются.
